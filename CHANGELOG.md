# Changelog

## Unreleased

- The validation flow of the designs (review of 19 October 2026): aggregates have a `kind` (`edit`, `creation`, `change-event`); an edit is applied at once (a conflict refuses it with 409 and its conflicts, nothing is held), a request to register a new organisation (`new-organisation`: the organisation is minted as the target, exists in the request only until approval, needs a KBO number the register and the pending creations do not hold, and is allowed per `creatableClassifications`, the "Wie beheert" table) or a veranderingsgebeurtenis (`change-event`, including the organisation's resulting fields) waits for ABB; what ABB requests itself is applied at once. `holdOnConflict` is gone. `new-organisation` operates on `change-event-results` too: the oprichting carries its result (the status the organisation starts with), which is what the organisation's veranderingsgebeurtenissen page lists.
- Statuses `informatie-gevraagd` and `afgehandeld`, steps `informatievraag` (ABB, with a question), `informatieantwoord` (the requester), `betwisting` (the requester contests a rejection: `afgekeurd` is no longer final) and `afhandeling` (the service applies an approved request: `goedgekeurd` is the decision, `afgehandeld` the applied state; an apply records both in one update, a failed apply leaves the afhandeling `mislukt`); `POST /change-requests` takes an optional `reason`, kept on the indiening.
- Visibility: everyone who is logged in sees every request (`pendingVisibleTo: everyone`; `involved` shows a waiting request to the requesting organisation, the organisation it is about and ABB only); the person who submitted a request and the texts of its steps are shown to the requesting organisation and ABB only; documents carry `kind`, `mine`, `target-name` and `target-classification`, the detail carries the submitted `operations`, a waiting creation's target carries `meta.pending`.
- `GET /change-requests`: oldest first (`sort=created`, or `-created`), `filter[kind]`, `filter[mine]`, `filter[requester]`, `filter[target-classification]`, `filter[created][gte|lte]`; `GET /change-requests/permissions` answers `can-decide` and `can-submit-change-event` with a target and `can-create` (the classifications the session may request) without one.
- Edits are the history of the data, not requests anyone acts on: `GET /change-requests` lists creations and change events only unless `filter[kind]` names `edit`; an edit that changes nothing is not stored (200, `data` null, `meta.unchanged`); an edit takes no validation steps, only a hertoepassing or an intrekking after a failed apply.
- Per aggregate `writable` (config): the fields it may change on an organisation. The kerngegevens may no longer change the werkingsgebied, the juridische vorm, the bijkomende kwalificaties, located-within or exact-match (a veranderingsgebeurtenis does), a vestiging only the sites; other fields may be carried unchanged, a changed one is a 422. Attributes are checked like relationships.
- `registration` (config): every classification the service registers, by the resource type it registers it as, the type of the oprichting and the classifications registered without a KBO number. A creation must match its classification's type and carry exactly one oprichting; a change-event request exactly one change event about its target; ABB's `can-create` lists every registered classification. `kind` and `pendingVisibleTo` are required, `statusScheme` is no longer read.
- KBO numbers: normalised to ten digits (a 422 otherwise), required for a creation unless its classification is `kboOptional`, one per organisation; unique also on an edit that changes it, at goedkeuring and hertoepassing (against the register) and at betwisting (also against waiting creations), under a lock per number; any spelling of "KBO nummer" is refused but the exact one, KBO mirror records hold no number; the 409 names a waiting request only to who may see it.
- ABB's own creation or change event that conflicts with newer values waits for ABB's goedkeuring with the token (rule `conflicts-wait-for-review`) instead of overwriting them. A hertoepassing is for ABB and the requesting organisation (`canReapply`).
- The apply no longer touches the request's status: it is read back (inserted values, replaced fields, deleted records, steps), run once more when incomplete, and only then the status is set, the new one added before the old one is removed; a failure is recorded under a step of its own, and when that fails too the answer is a 500 that says the outcome is unknown. A submission is read back too and withdrawn by the service when it stays incomplete. A request without a status, or with two, is found and takes the status of its last step.
- The lookups of other requests (pending KBO numbers, competing requests, steps) are small anchored queries: on an empty change-requests graph Virtuoso refused them on its cost estimate, so the first creations of a new deployment failed. Steps are read by request URI after the visibility check.
- Limits: 100 operations, 100 values per field, 10000 characters of text, pages within Virtuoso's row limit; the set merge is linear. A create must be linked to the organisation through the request, and an inverse link on a create must be given on the forward side too. A record another organisation links to cannot be deleted (409). Unknown filters are a 400, a body that is not JSON a 415, an id with a control character a 404; texts with control characters, impossible dates and non-web links are a 422.
- Visibility: in `involved` mode everyone sees the decided requests (not only the applied ones); the error of a failed apply is shown to the requesting organisation and ABB only; a creation's target carries `meta.registered: false` and `meta.pending` while it waits; `filter[target]` finds a waiting creation by its minted uuid; a request whose organisation is gone can still be read and closed; an ambiguous session is a 401.
- app-lokale-verkenner keeps the organisation data in a graph of its own, `http://mu.semte.ch/graphs/administrative-unit` (as in OP), which only logged-in sessions read: the service's `APPLICATION_GRAPH`; `scripts/e2e-mock-login.sh` reads and cleans the organisation data there (`ORGS_GRAPH`) and checks that a visitor without a session reads none of it; the docs name the graph.
- The image turns off the template's logging of every query and of the authorization headers; `npm test` runs on Node 20 and parses every query the tests drive (sparqljs, a dev dependency `npm run setup` installs); `scripts/e2e-mock-login.sh` checks the rules above, refuses a SPARQL endpoint that is not local and puts everything back, also when interrupted.

## 0.1.0

- Initial version: `POST /change-requests` turns the JSON:API operations of one aggregate into RDF version objects, checks the edit policy, writes the request and applies it in one SPARQL update inside the service scope; `GET /change-requests`, `GET /change-requests/:id` and `GET /change-requests/permissions`; the resources model is read from the mounted mu-cl-resources JSON files, with the datatype table of mu-cl-resources; unit tests and `scripts/integration.sh`.
- Data model, checked against OSLO and the lblod apps (`vocabulary/change-requests.ttl` defines the `cr:` terms and their alignments): a request (`cr:ChangeRequest`) names the requesting organisation (`pav:createdBy`) and the person who submitted it (`dct:creator`); its steps (`cr:Action`) are `dct:isPartOf` it, ordered by `schema:position`, taken by a `foaf:Person` or the service (`prov:wasAssociatedWith`); a proposed version (`cr:ProposedVersion`) is `dct:isVersionOf` its record and marks its `cr:operation` with `as:Create`, `as:Update` or `as:Delete`; record states (`cr:RecordState`) hold the values a version started from (`cr:base`) and the values an apply replaced (`prov:invalidated`); statuses and step types are UUID concepts, published as SKOS code lists by app-lokale-verkenner's migrations.
- Every id an operation touches or links to must belong to the target organisation's aggregate (reachable from the target); an organisation is only ever updated, and only the target itself.
- Per-key semantics: a version changes only the keys its document carries (`cr:changesProperty`); a relationship outside the aggregate must be unchanged, references (`references` per aggregate: locations, concepts, site types) are part of the version; `organizations` is a member of the `site` aggregate.
- The apply is idempotent and retried once; a failed request can be applied again from its stored versions with `POST /change-requests/:id/apply` (`cr:operation`, `cr:masterUuid`, `cr:changesProperty` on every version).
- A relationship to a type the loaded model files do not define is logged and left out instead of stopping the service (app-lokale-verkenner loads only `domain.json` and `auth.json`).
- `scripts/e2e-mock-login.sh`: the end-to-end flow against app-lokale-verkenner through mu-identifier with mock-login sessions.
- A create writes the class tree of its type; `url` and `uri-set` values are checked to be IRIs; `MAX_BODY_SIZE=5mb` in the image, 413 above it; mu-identifier 1.11.0 or later required and checked by the integration script.
- The session resolves to the account, the acting organisation and the person of the account (`foaf:account`); the person is who the service records, also as `ext:lastModifiedBy` on what a request changes. A session without a person is a 401.
- Steps: every request carries an ordered trail of steps (indiening, goedkeuring, afkeuring, intrekking, hertoepassing; `wijziging` reserved) with position, time, agent, acting organisation, rule, reason and, when an apply failed, an `oslc:Error` (`task:error`); its status is the status of the last step; the versions hang off the indiening step.
- `POST /change-requests/:id/steps`: ABB approves (goedkeuring, conflicts re-checked live, `override`) or rejects (afkeuring, reason required), the requester or ABB withdraws (intrekking), a failed request is applied again (hertoepassing, still also `POST /change-requests/:id/apply`); policies `canDecide` and `canWithdraw`; 409 for a step the status does not admit.
- Base values: an update may carry `meta.base`; a key the user did not change or that the master already holds is not written, a key someone else changed since is a conflict and stays in the version; every update version records the state it started from; an update that changes nothing leaves no version and a request without versions does not stamp `dct:modified`.
- Conflicts with their competing requests (other pending requests on the same key) in the documents, at submission and live for pending requests; `autoApprove` is `[holdOnConflict, always]`, so a conflicting request waits for ABB.
- Submissions and steps are serialised per target organisation with an in-process lock (holds for one service instance).
- The apply's WHERE anchors on the request's type, so a retry after an attempt that removed the old status still inserts; a stored `harvest-source` value (`prov:wasGeneratedBy` literal) is a value like any other.
- Needs `cr:ChangeRequest`, `cr:Action`, `cr:ProposedVersion`, `cr:RecordState`, `rdf:Statement` and `oslc:Error` in the change-requests graph spec of sparql-parser.
- A delete may carry `meta.base`; a tombstone's base state records the base of every key and the links to its master (`cr:incomingLink`, one `rdf:Statement` each), and conflicts on a value set or a link made since, at submission and before a goedkeuring.
- To-many relationships and set attributes merge the request's additions and removals into the current value instead of replacing it; they no longer conflict.
- A goedkeuring overrides conflicts only with their `conflicts-token` (GET, or the 409) as `override`. Every applying step records the states it replaced; the conflicts it overrode are derived from them (`overridden-conflicts` in the API).
- A request that updates a record deleted since is refused for goedkeuring and hertoepassing (409 `missing-records`); conflicts carry `master-exists`; afkeuring and intrekking also follow `mislukt`.
- `GET /change-requests` is paged (`page[number]`, `page[size]`, `meta.count`, `links`) with `filter[status]`; steps, versions and current values are read per page, in batches under `SPARQL_MAX_ROWS`.
- Competing requests are looked up for every key a request writes and listed in `competing`, also without a conflict.
- A hertoepassing is refused only after a later request that changed something.
- A tombstone does not remove the links to its master from stored versions and record states.
- A request that is applied withdraws the older pending requests of the same organisation it fully replaces (rule `superseded-by-own-request`); the answer lists them as `superseded`, and a withdrawn request names the newer one (`dct:isReplacedBy`, `replaced-by` in the API).
